# Проект: ускорение инференса Nemotron

## Задача

Ускорить инференс — генерацию ответов — моделей NVIDIA Nemotron на доступном нам железе и понять,
от чего зависит результат. Способов много: квантизация, спекулятивный декодинг, экономия рассуждений,
приёмы для MoE и другие (`docs/families.md`). Какие пробовать, решает исследователь по статьям
и по результатам своих экспериментов. Обязательное условие — ускорение не должно заметно портить ответы,
поэтому каждую идею проверяем и по скорости, и по качеству.

Изначально проект был только про спекулятивный декодинг для Nano 9B v2. Потом цель расширили до
ускорения инференса вообще.

Работаем с тремя группами моделей, от простого к сложному:

| Группа | Модели | Где считаем | Что можно мерить |
|---|---|---|---|
| 1. Плотные гибриды | Nemotron Nano 9B v2, Nemotron 3 Nano 4B | Kaggle 2× T4, ноутбук, Mac, ПК | скорость, качество, внутренности модели |
| 2. MoE у себя | Nemotron 3 Nano 30B-A3B, Lightning 3.5 (30B-A3B) | ноутбук Игоря, Kaggle 2× T4 | скорость, качество |
| 3. Super | Nemotron 3 Super 120B-A12B, Nemotron 3.5 Super VL | API Nebius | согласие с Nano, токены, деньги, точность — но не скорость |

Про группу 3: скорость провайдера по времени не наша и шумная, поэтому «ускорение Super через Nano»
оцениваем офлайн. Например, по logprobs считаем, сколько токенов черновика Nano приняла бы Super,
и переводим это в ускорение по формуле. Оценка бюджета: вся программа офлайн-приёма — ~$21, с запасом ~$32
(это ~750 прогонов Spec-Bench без рассуждения). Остальное из $150 — на экономию рассуждений, каскады и SpecReason.

## Команда

| Кто | Железо | Время |
|---|---|---|
| Игорь (ведёт проект) | ноутбук с Radeon 780M и 32 ГБ общей памяти; сервер ~10 ГБ диска, 1 ГБ RAM, работает постоянно | ~4 ч в день |
| Руслан | лёгкий Mac | ~4 ч в день |
| Дима | ПК на Windows, 16 ГБ RAM | ~4 ч в день |

У каждого свой аккаунт Kaggle. Все трое знают Python и PyTorch на начальном уровне. Аренду GPU не используем.

## Роли

| Роль | Чем занимается | Главный результат |
|---|---|---|
| Исследователь | Ищет и придумывает способы ускорения, сам пишет код экспериментов на функциях ядра, разбирает результаты | Выводы: что и насколько ускоряет |
| Разработчик ядра | Пишет общую библиотеку `fastinfer`: загрузка моделей, генерация, замер скорости и качества, тесты | Ядро, которому можно верить |
| Инфраструктурщик | Делает так, чтобы эксперимент запускался одной командой на нужном железе, а результаты сами попадали в хранилище | Диспетчер, запуск на Kaggle и своих устройствах |

Кто какую роль занимает: _заполнить_. Исследователь и разработчик ядра могут со временем меняться ролями:
основа ядра пишется в начале, потом разработчик ядра может стать вторым исследователем (например, взять MoE или Super).

Граница между ролями — эксперимент: короткий конфиг плюс, если нужно, код в репозитории.
Результат — папка с файлами в общем формате (`docs/core_api.md`).

## Ресурсы

| Ресурс | Для чего | Ограничения |
|---|---|---|
| Kaggle, 2× T4 (на каждого) | скорость и качество 4B, 9B, 30B-A3B; HF-прототипы; маленькое обучение | ~30 ч в неделю сессий с GPU, до 12 ч на сессию; T4 — sm75, 16 ГБ, 320 ГБ/с |
| Ноутбук Игоря, 780M | llama.cpp на Vulkan, 30B-A3B, ночные прогоны | только когда Игорь его подключил; ~90–120 ГБ/с |
| Mac Руслана, ПК Димы | малые модели, анализ на CPU, квантизация, разработка | CPU или Metal, мало памяти |
| Сервер Игоря | диспетчер: очередь, учёт, запуск Kaggle | ничего не считает; 10 ГБ диска, 1 ГБ RAM |
| Nebius Token Factory | ответы Super, качество 30B-A3B и Lightning | $150, только API |
| Hugging Face | сырые результаты, наши кванты, кэш ответов API | 100 ГБ приватного хранилища бесплатно |
| GitHub | публичный репозиторий, CI | Actions для публичных репозиториев бесплатны |
| Colab | ручная отладка | бесплатный Colab нельзя подключать как исполнитель |

Квота Kaggle, по всему, что удалось найти, считается по времени сессии, а не по числу карт: сессия на 2× T4
списывает столько же, сколько на одной карте. Официальный текст не прочитан — проверить по счётчику (`docs/facts.md`).

## Как идёт эксперимент

1. Исследователь создаёт `experiments/<ГГГГ-ММ-ДД-имя>/` с `README.md` (гипотеза, семейство) и `config.yaml`;
   `run.py` — только если идея не укладывается в конфиг.
2. Изменения попадают в репозиторий через PR. Задача на запуск ссылается на конкретный коммит.
3. Исследователь отправляет задачу диспетчеру: путь к конфигу, коммит, устройство.
4. Диспетчер запускает её на Kaggle (через API) или отдаёт агенту на подключённом ноутбуке.
5. На исполнителе ядро читает конфиг и пишет папку результата (`docs/core_api.md`).
6. Сырые результаты уходят на Hugging Face, короткая сводка — в Telegram и в PR с результатами.
7. Исследователь пишет выводы в `README.md` эксперимента и в `reports/`.

## Принятые решения и почему

1. **Цель — ускорение инференса вообще**, а не только спекулятивный декодинг: у гибридов Mamba и у MoE
   выигрыш даёт много разных приёмов (`docs/families.md`).
2. **Порядок групп**: плотные → MoE у себя → Super через API. От простого к сложному: сначала то,
   где можно мерить всё.
3. **Деньги Nebius — только на API Token Factory**, цели — обе модели Super.
4. **Исследователь пишет код экспериментов сам**, на функциях ядра; ядро — общий фундамент.
5. **Основной движок — llama.cpp**: он работает на всех наших устройствах и уже умеет спекуляцию
   и откат состояния для гибридов. HF transformers — для прототипов и анализа; заявления о скорости
   делаем только по llama.cpp или по другому быстрому движку.
6. **Общий API — это два формата**: `config.yaml` на входе и папка результата на выходе.
7. **Сервер Игоря — только диспетчер**: Python и SQLite. ClearML и подобное не поместятся в 1 ГБ RAM.
8. **Kaggle запускаем через API** («толкаем» задачу), ноутбук подключается агентом («тянет» задачи,
   потому что он за NAT; включается «кнопкой на ночь»). Colab — только вручную.
9. **Репозиторий публичный** (`nemotron-speedmap`), все трое закрепляют его в профиле GitHub.
10. **Разработчику ядра — план и сигнатуры**, а не готовый код: он хочет разобраться и реализовать сам.
    В репозиторий сначала кладём только контракт (`docs/first_task.md`).
11. **Контракт ядра меняется только через PR**, который смотрят все трое.
12. **Начинаем с простого**: сначала запуск одной командой вручную, очередь и агенты — потом.

## Открытые вопросы — проверить

- Квота Kaggle при 2× T4: 10 минут сессии — это 10 минут квоты или 20?
- Сколько GPU-сессий одновременно разрешено на аккаунт Kaggle; сколько CPU и RAM у машины (`nproc`, `free -g`).
- Совпадают ли токенизаторы 4B, 9B, 30B-A3B, Lightning и Super (словарь у всех 131 072, но этого мало).
- Работает ли vLLM на T4 (FlashAttention-2 нет; остаются бэкенды Triton и Flex).
- Нет ли переполнений fp16 на T4 у моделей, обученных в bf16 (у ReLU² большие значения).
- Работают ли быстрые ядра Mamba (mamba-ssm, causal-conv1d) на T4 в HF.
- Есть ли GGUF Lightning 3.5 с MTP-слоями; точные имена репозиториев 4B и Lightning на HF.
- Имена моделей в Nebius — взять из `GET /v1/models`.
- На какой ОС ноутбук Игоря (от этого зависит агент и сборка llama.cpp).

## Словарик

| Термин | Что значит |
|---|---|
| Инференс | Генерация ответа уже обученной моделью |
| Prefill и декодирование | Чтение промпта (параллельно, упирается в вычисления) и генерация по токену (упирается в память) |
| Батч | Сколько последовательностей идут одним проходом; батч 1 — один пользователь |
| ПСП и потолок | Пропускная способность памяти, ГБ/с; потолок ток/с = ПСП ÷ байты на токен |
| Цель и черновик | Модель, которую ускоряем, и дешёвый источник догадок о её следующих токенах |
| Спекулятивный декодинг | Черновик предлагает γ токенов, цель проверяет их за один проход; ответ не меняется |
| γ, α, c, τ | Длина черновика; доля принятых токенов; цена шага черновика относительно шага цели; среднее число токенов за проход цели |
| MTP | Встроенная в модель голова, которая предсказывает несколько следующих токенов (есть у Super и Lightning) |
| Квантизация, квант | Хранение весов в 8, 6, 4 и меньше битах; квант — формат GGUF (Q8_0, Q4_K_M…) |
| Mamba, состояние | Слой, который помнит текст одним сжатым состоянием фиксированного размера вместо KV-кэша |
| MoE, эксперт, top-k | Модель из «экспертов»: на токен работает k из N (у 30B-A3B — 6 из 128 плюс общий) |
| ReLU² | Квадрат ReLU — активация в MLP у Nemotron; даёт точные нули |
| Без потерь | Ответы совпадают с базой (в жадном режиме — побайтно) |
| logprobs | Логарифмы вероятностей токенов, которые отдаёт API или движок |
